# 001 — Phase 1 MVP: Initialize Core Platform

- **Status:** active
- **Owner:** Engineering
- **Last updated:** 2026-06-15

---

## Goal

Establish the complete Phase 1 MVP of the AI-driven coding academy platform: a fully operational, stateless, database-free client-server loop covering course browsing, lesson viewing, progress tracking, and mock AI mentoring — all backed by a centralized in-memory store.

---

## Scope

### In Scope
- `server/data/store.py` — centralized in-memory singleton (seed data + progress state)
- Pydantic schemas for all Phase 1 data contracts
- FastAPI routers for all five Phase 1 endpoints
- `CourseService`, `ProgressService`, `ChatService` application services
- `BaseAIProvider` abstraction + `MockAIProvider` implementation (Hebrew scaffolded responses)
- React/Vite/TypeScript/React Router/Material UI frontend workspace scaffold
- CORSMiddleware on the FastAPI app allowing the Vite dev port

### Out of Scope (Phase 1 Hard Boundary)
- Real AI providers (OpenAI, Gemini)
- Admin panel or instructor dashboard
- Authentication, billing, or multi-tenancy
- Database, ORM, or persistence layer
- Portfolio Architect, Technical Interviewer, Custom Codex

---

## Assumptions

1. Python 3.11+ and Node 20+ are available in the development environment.
2. A single active user (`user_id: "default_user"`) is assumed throughout Phase 1; no session or token system is required.
3. `server/data/store.py` is imported as a module singleton — Python's module import cache guarantees all services read and mutate the same in-memory object.
4. `asyncio.Lock` instances are created at the service layer (not in `store.py`) to manage concurrent write access to the progress state dictionary.
5. Completion percentage is calculated dynamically at write time inside `ProgressService` by counting total lessons across all sections via an injected `CourseService` instance.
6. The frontend communicates with the backend exclusively via JSON over HTTP (Fetch API or Axios); no WebSocket is required in Phase 1.
7. All JS/TS files must have zero trailing semicolons as mandated by `.rule/coding-rules.md`. Where a leading semicolon is needed for syntax safety, it is placed at the start of the line.
8. All API errors return the standard JSON error shape defined in `.rule/error-handling-rules.md` — no stack traces or raw exceptions are leaked to the client.
9. Seed data is static and hardcoded in Hebrew or English at the implementer's discretion; content quality is secondary to structural correctness at this stage.

## Steps

### Step 1 — Backend: Central Data Store (`server/data/store.py`)

**Deliverables:**
- `server/data/store.py`

**Tasks:**
1. Define the `COURSES_DB` dictionary — a `dict[str, dict]` keyed by `course_id`.
2. Populate seed data satisfying the minimum structural requirement:
   - **1 course** (e.g., `"course-01"`) with `id`, `title`, `description`, `image_url`.
   - **2 sections** within that course (e.g., `"section-01"`, `"section-02"`), each with `id`, `course_id`, `title`, `order`.
   - **3 lessons** within each section (6 total), each with `id`, `section_id`, `title`, `content` (Markdown string), `order`.
3. Define the `PROGRESS_DB` dictionary — a single module-level `dict` matching the `Progress` schema, initialized with:
   - `user_id`: `"default_user"`
   - `current_course_id`: `"course-01"`
   - `current_section_id`: `"section-01"`
   - `current_lesson_id`: first lesson id (e.g., `"lesson-01-01"`)
   - `completion_percentage`: `0.0`
4. Do not expose any lock here — locking is the service layer's responsibility.

**Verification:** Import `store.py` in a Python REPL; confirm `COURSES_DB` and `PROGRESS_DB` are accessible and structurally valid.

### Step 2 — Backend: Pydantic Schemas (`server/schemas/`)

**Deliverables:**
- `server/schemas/course.py`
- `server/schemas/progress.py`
- `server/schemas/chat.py`

**Tasks:**
1. **`course.py`** — define:
   - `Course` (summary model): `id`, `title`, `description`, `image_url`
   - `Lesson`: `id`, `section_id`, `title`, `content`, `order`
   - `Section`: `id`, `course_id`, `title`, `order`, `lessons: list[Lesson]`
   - `CourseDetail`: `id`, `title`, `description`, `image_url`, `sections: list[Section]`
2. **`progress.py`** — define:
   - `ProgressUpdatePayload`: `current_lesson_id: str` (strictly only this field per spec)
   - `Progress`: `user_id`, `current_course_id`, `current_section_id`, `current_lesson_id`, `completion_percentage: float`
3. **`chat.py`** — define:
   - `ChatInput`: `user_message: str`, `course_id: str`, `lesson_id: str`, `student_level: Literal["beginner", "intermediate", "advanced"]`
   - `ChatResponse`: `response: str`
4. All models use `model_config = ConfigDict(frozen=False)` or standard Pydantic v2 configuration where appropriate.

**Verification:** `from server.schemas.course import CourseDetail` imports cleanly with no errors.

### Step 3 — Backend: Application Services (`server/services/`)

**Deliverables:**
- `server/services/course_service.py`
- `server/services/progress_service.py`
- `server/services/chat_service.py`

**Tasks:**

#### 3a. `CourseService` (`server/services/course_service.py`)
1. Import `COURSES_DB` from `server.data.store`.
2. Implement `get_all_courses() -> list[Course]` — returns summary models from the store.
3. Implement `get_course_detail(course_id: str) -> CourseDetail | None` — builds a fully nested `CourseDetail` from the flat store structures; returns `None` if not found.
4. Implement `get_total_lesson_count(course_id: str) -> int` — sums all lessons across all sections of a given course. Used by `ProgressService`.

#### 3b. `ProgressService` (`server/services/progress_service.py`)
1. Import `PROGRESS_DB` from `server.data.store`.
2. Declare a module-level `asyncio.Lock` (e.g., `_progress_lock = asyncio.Lock()`).
3. Accept a `CourseService` instance via constructor injection to resolve the one-way dependency (`ProgressService` → `CourseService`).
4. Implement `async get_progress() -> Progress` — reads and returns the current `PROGRESS_DB` state as a `Progress` model.
5. Implement `async update_progress(payload: ProgressUpdatePayload) -> Progress`:
   - Acquire `_progress_lock` via `async with`.
   - Look up the provided `current_lesson_id` in the store to derive `current_section_id` and `current_course_id`.
   - Raise `HTTPException(404)` using the standard error shape if the lesson id is not found.
   - Call `course_service.get_total_lesson_count(course_id)` to obtain the denominator.
   - Determine the lesson's position (its `order` field) to compute numerator.
   - Calculate `completion_percentage = (lesson_order / total_lesson_count) * 100.0`.
   - Mutate `PROGRESS_DB` in-place; return the updated `Progress` model.

#### 3c. `ChatService` (`server/services/chat_service.py`)
1. Import `BaseAIProvider` from `server.providers.base_provider`.
2. Accept a `BaseAIProvider` instance via constructor injection.
3. Implement `async generate_response(payload: ChatInput) -> ChatResponse`:
   - Delegate to `provider.generate(payload)`.
   - Wrap any provider exception in an `HTTPException(502)` using the standard error shape (no raw traces exposed).

**Verification:** Unit-importable with no circular import errors. `ProgressService` accepts a `CourseService` argument and lock is module-level.

### Step 4 — Backend: AI Provider Abstraction (`server/providers/`)

**Deliverables:**
- `server/providers/base_provider.py`
- `server/providers/mock_provider.py`

**Tasks:**

#### 4a. `BaseAIProvider` (`server/providers/base_provider.py`)
1. Define an abstract base class `BaseAIProvider` using Python's `abc.ABC`.
2. Declare abstract method `async generate(payload: ChatInput) -> ChatResponse`.

#### 4b. `MockAIProvider` (`server/providers/mock_provider.py`)
1. Implement `MockAIProvider(BaseAIProvider)`.
2. Implement `async generate(payload: ChatInput) -> ChatResponse` with conditional Hebrew response logic:
   - **Keyword triggers** (case-insensitive substring match on `payload.user_message`):
     - `"error"` or `"bug"` → return a scaffolded hint response. Do not give the direct answer. Include `[רמה: {student_level}]` and `[הקשר: {lesson_id}]` tags embedded naturally in Hebrew text.
     - `"help"` → return a guiding question that pushes the student toward the solution.
     - Default (no keyword match) → return a brief Hebrew acknowledgement that includes the lesson context.
   - Response shape: `ChatResponse(response=<hebrew_string>)`.
3. Response latency must remain under 500ms (no artificial sleep unless testing).

**Verification:** Calling `MockAIProvider().generate(sample_payload)` with keyword `"bug"` returns a Hebrew string containing `[הקשר:` and `[רמה:`.

### Step 5 — Backend: FastAPI Routers (`server/routers/`)

**Deliverables:**
- `server/routers/courses.py`
- `server/routers/progress.py`
- `server/routers/chat.py`

**Tasks:**

#### 5a. `courses.py`
1. Create an `APIRouter(prefix="/api/courses", tags=["courses"])`.
2. `GET /api/courses` → calls `course_service.get_all_courses()` → returns `list[Course]`.
3. `GET /api/courses/{course_id}` → calls `course_service.get_course_detail(course_id)` → returns `CourseDetail`; raises `HTTPException(404)` with standard error shape if `None`.

#### 5b. `progress.py`
1. Create an `APIRouter(prefix="/api/progress", tags=["progress"])`.
2. `GET /api/progress` → calls `await progress_service.get_progress()` → returns `Progress`.
3. `POST /api/progress` → accepts `ProgressUpdatePayload` body → calls `await progress_service.update_progress(payload)` → returns updated `Progress`.

#### 5c. `chat.py`
1. Create an `APIRouter(prefix="/api/chat", tags=["chat"])`.
2. `POST /api/chat` → accepts `ChatInput` body → calls `await chat_service.generate_response(payload)` → returns `ChatResponse`.

**Error contract:** All non-2xx responses follow the shape:
```json
{
  "error": {
    "code": "<machine_readable_code>",
    "message": "<human_readable_summary>",
    "details": null
  },
  "requestId": "<uuid>"
}
```

**Verification:** `curl http://localhost:8000/api/courses` returns a JSON array with at least one course object.

**Deliverables:**

## Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Circular imports between `ProgressService` and `CourseService` | Medium | High | Enforce one-way dependency: `ProgressService` imports `CourseService`; `CourseService` never imports `ProgressService`. Validate with a clean `python -c "from server.main import app"` before any further work. |
| `asyncio.Lock` misuse in sync context | Low | Medium | All `ProgressService` methods that acquire the lock must be `async def`. FastAPI route handlers must also be `async def`. |
| Trailing semicolons accidentally introduced in generated frontend code | Medium | Low (rules violation) | Run `grep -rn ";$" client/src/` as part of the validation checklist before marking this plan `done`. |
| Progress calculation edge case: lesson not found in store | Low | Medium | `update_progress` performs an explicit lookup before mutating state and raises `HTTPException(404)` — no silent corrupt state. |
| Seed data structural mismatch causing runtime `KeyError` | Low | High | Services must access `COURSES_DB` via `.get()` with `None` fallback, not direct key access, to prevent unhandled exceptions. |
| Vite proxy misconfiguration causing frontend to hit CORS directly | Low | Medium | Validate proxy in `vite.config.ts` early; document the exact `server.proxy` config block in Step 7. |

## Rollout Order

Execute steps sequentially. Each step's verification must pass before the next step begins.

```
Step 1: server/data/store.py          ← Foundation: all services depend on this
Step 2: server/schemas/               ← Contract definitions used by steps 3-5
Step 3: server/services/              ← Business logic; no router dependencies
Step 4: server/providers/             ← AI abstraction layer; depends on Step 2
Step 5: server/routers/               ← HTTP layer; depends on steps 2-4
Step 6: server/main.py                ← Assembly; wires all layers together
Step 7: client/                       ← Frontend scaffold; can proceed once Step 6 is verified
```

## Rollback

Because this is a greenfield initialization plan with no existing production data or deployed services, rollback is equivalent to reverting the generated files.

- **Code rollback:** Delete `server/` and `client/` directories to return to a clean repository state.
- **Plan status:** If implementation is abandoned mid-way, set `Status: superseded` and create a new plan documenting the revised approach.
- **No database migrations or external state mutations occur in Phase 1** — rollback carries zero data-loss risk.
